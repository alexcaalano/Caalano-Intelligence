# Product register and gross-profit metrics - agreed design (not yet built)

Agreed with Alex on 2026-09-05. Build this when clients have finished testing
the CRM's conditional required fields. Nothing here is implemented yet.

## What it delivers

Gross profit per won deal, and from it: gross profit next to Revenue, CAC to
gross profit ratio, gross profit ROAS, contribution after ads (GP less spend),
cash gross profit, a product-mix table (units won, revenue, GP by product, and
product by channel / campaign), and break-even cost per lead per product. All
of it follows the pipeline picker, channel toggle and date range like the
Cash position row (v3.480.0), and is per-client switchable in Settings.

## Where each piece lives

1. **Caalano Systems (GHL)** - one dropdown opportunity custom field,
   "Product / service sold" (dataType SINGLE_OPTIONS). The client's team picks
   it. It should sit in the same "marked as Won" required-field rule as Lead
   Value and Cash Collected, so every new win carries a product. The name
   should be the same on every client so 360 finds it without setup; match it
   with a loose regex the way Cash Collected is matched (`/product|service/i`
   on a SINGLE_OPTIONS field, or an explicit field pick in Settings as the
   fallback).
2. **360 Settings - Products tab (the register)** - per client. Reads the
   dropdown's options from the field definition (`picklistOptions` on
   `GET /locations/{id}/customFields?model=opportunity`, already cached hourly
   by `oppCustomFields` in `netlify/lib/ghl.mjs`). Against each product the
   agency enters **cost to fulfil in dollars** (a margin percentage can be
   shown, but dollars are stored - a discount then hits GP dollar for dollar,
   which is the truth). Margins never go into the CRM, so reps never see them.
   Stored in `SETTINGS.clients[id].products` (settings.mjs allow-list already
   has `clients`).
3. **The drill** - `buildCcDrill` reads the product option off each won
   opportunity exactly as it reads Cash Collected (`oppCashValue` pattern:
   `o.customFields[] {id, fieldValueString}`), resolves it through the
   register, and computes GP = deal value - cost to fulfil. Rolls up totals,
   per pipeline (`pipeContribution[].gp`), per channel (`closeByChannel[].gp`
   and `chan[k].gp`), per product, and per won deal (`revenue.deals[].product`,
   `.gp`). `lensCc` carries it per pipeline like `cash`.

## Identity: the alias approach (decided)

The CRM gives **no stable ID for dropdown options**. Verified 2026-09-05 on
Nexia: the field definition lists options as plain strings, and the object
schema (`GET /objects/opportunity?fetchProperties=true`) returns each option
as `{key, label}` with key equal to label. The opportunity stores the option's
text. A rename changes what new deals carry; old deals keep the old text.

So the register owns identity:

- Each product has its own stable id generated by 360 (e.g. `prd_<random>`),
  a display name, cost to fulfil, and an **alias list** of CRM option texts
  that map to it. Matching is exact on normalised text (trim, case-fold,
  collapse whitespace) - never fuzzy at read time, so it never mis-costs.
- Same pattern as the UTM campaign aliases already in the app (`loadAliases`
  / `lrFoldDict`); reuse the fold helpers where they fit.
- On each register load, compare the CRM's current option list with all known
  aliases. An option no longer present + an unknown option appearing =
  probable rename: the register flags it and suggests "this looks like a
  rename of X" (fuzzy suggestion is fine here, it is a human-confirmed step).
  One click adds the new text as an alias; cost and history carry on.
- Until confirmed, deals carrying an unknown option sit under **"Unknown
  product"** in every rollup - never dropped, never costed.
- Won deals with no product picked sit under **"Unassigned"**, with a coverage
  figure ("n of m won deals have a product"), like cash entered.

## Rules and caveats to honour

- A deal with no product is unknown, not zero GP. Same principle as cash.
- Cost changes apply to all history in v1 and the UI says so. Dated costs
  (effective-from) are the later upgrade if a client needs them.
- Per-product CAC allocates spend by **won share**, not lead share - a lead has
  no product until it wins. Say so on the tile.
- One product per deal (single select). Bundles are their own option.
- Required fields only bite in the CRM UI: wins marked by a workflow, payment
  trigger or API skip the prompt. Check how each client's wins get marked.
- Cash Collected is a running total; pair with a CRM task when cash < value so
  balances get updated. Reps must enter cash actually received, not the value.
- The Funnel Forecaster's single account-wide gross margin field could later
  be derived from product mix instead of typed.
- Later, with a `locations/customFields.write` scope (needs app
  re-authorisation), 360 could push the option list into the CRM dropdown so
  the register becomes the single place products are managed.
